# 3. Serve the API over HTTPS at the ingress

Status: accepted

## Context

ADR 0002 protects writes with a Bearer token. Without transport encryption that token crosses the network
in clear text, so anyone on the path can read it and replay it. Authentication and encryption are separate
layers, and the first is not worth much without the second.

The cluster is local (kind), the host name is `posts.local`, and the evaluator must be able to run everything
with one command.

## Options

1. Keep HTTP and say so. The token is exposed; not acceptable once the token exists.
2. HTTPS at the ingress with a self-signed certificate generated by `bootstrap.sh` (openssl).
3. A local certificate authority such as mkcert. The certificate is trusted by the browser, but it needs another
   tool installed and changes the trust store of the machine.
4. cert-manager with a real issuer (Let's Encrypt or an internal CA). The right answer in a cloud cluster, but it
   needs a public DNS name and a reachable ingress, neither of which exists on a laptop.
5. Terminate TLS in the application. Every pod would carry a key, and the ingress could no longer inspect or route.

## Decision

Option 2 now, option 4 as the documented production path.

- `bootstrap.sh up` creates the Secret `posts-api-tls` (type `kubernetes.io/tls`) with a self-signed RSA 2048
  certificate valid for 365 days, with `posts.local` as a subjectAltName (modern clients ignore the common
  name). The private key exists only in a temporary directory and in that Secret, never in Git or in the
  image. An existing Secret is kept.
- The Ingress references the Secret, and an annotation restricts it to Traefik's `websecure` entrypoint: **the
  API is served over HTTPS only.** On the plain HTTP port the host answers 404, so a client that forgets `https://`
  gets an error instead of an unencrypted working API. A redirect was considered and not used: with the kind port
  mapping (443 on the node is 18443 on the host) Traefik would redirect to port 443, which is not reachable, and a
  redirect does not protect a token that was already sent in the first request anyway.
- Clients and tests verify the certificate: `curl --cacert` with the certificate read from the Secret and
  `--resolve posts.local:18443:127.0.0.1`. Nothing uses `-k`. The smoke test checks that HTTPS validates, that
  plain HTTP is not served, and that an unknown host gets 404.
- The chart value `ingress.tls.secretName` (default `posts-api-tls`) turns this on; empty serves plain HTTP.

## Consequences

- A self-signed certificate is not trusted by browsers or by `curl` unless given with `--cacert`; a browser
  shows a warning. No public authority issues certificates for `posts.local`, so this cannot be avoided locally.
  The certificate is its own trust anchor, so anyone who can read the Secret can pin it; its private key is as
  sensitive as the token.
- It expires after a year. To renew: delete the Secret `posts-api-tls` and run `bootstrap.sh up`; the ingress
  picks the new certificate up. There is no automatic renewal, which is what cert-manager would add.
- Kubernetes Secrets are base64, not encrypted. In a real cluster enable encryption at rest and restrict who can
  read Secrets.
- TLS ends at the ingress: traffic between Traefik and the pods, and between the pods and the database, is
  plain. A service mesh or per-hop TLS would be the next step if the network inside the cluster is not trusted.
- In a cloud cluster the same Ingress works with cert-manager: replace the Secret by a `Certificate` and an
  issuer; no application change is needed.
